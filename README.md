# 🗺️ Карта Пространства — ТТК (Хакатон 2026)

Сервис для навигации внутри зданий и на мероприятиях с интерактивным 2D-планом и 360° виртуальными панорамами.

---

## 🚀 Быстрый старт через Docker

Вам **не нужно** ставить вручную Python, Node.js или базы данных. Всё поднимается одной командой:

- **Windows:** дважды кликните по файлу **`start.bat`** (или в PowerShell: `.\start.ps1`)
  *(Скрипт сам определит, как у вас установлен Docker — через Docker Desktop или WSL)*
- **macOS / Linux:** в терминале запустите `./start.sh`

### Сервисы доступны по адресам:
- 📱 **Клиент посетителя (Mobile Web):** [http://localhost:3000](http://localhost:3000)
- 🛠 **Студия организатора (Admin Studio):** [http://localhost:3001](http://localhost:3001)
- 🚀 **Backend API & Swagger docs:** [http://localhost:8000/docs](http://localhost:8000/docs)

Остановка всех контейнеров:
- **Windows:** запустить `stop.bat` или `.\stop.ps1`
- **macOS / Linux:** `./stop.sh`

## 🔐 Авторизация и два варианта входа

В проекте два самостоятельных входа — как и два интерфейса:

| Вход | Адрес | Роль | Что доступно |
| :--- | :--- | :--- | :--- |
| **Посетитель** | [http://localhost:3000](http://localhost:3000) | `user` | Карта, POI, маршруты, 360°-панорамы |
| **Организатор** | [http://localhost:3001](http://localhost:3001) | `admin` | Студия: план, POI, граф, загрузка панорам |

На экране входа есть переключатель роли: он ведёт в соседний интерфейс. Зарегистрироваться можно прямо на экране входа. Для создания аккаунта **организатора** нужен код-приглашение (по умолчанию `TTK-ADMIN-2026`), обычный посетитель регистрируется без кода.

### Демо-аккаунты

Создаются автоматически при первом запуске бэкенда:

| Роль | Email | Пароль |
| :--- | :--- | :--- |
| Организатор | `admin@ttk.local` | `Admin12345!` |
| Посетитель | `user@ttk.local` | `User12345!` |

> Для боевого запуска обязательно задайте свои `TTK_ADMIN_PASSWORD`, `TTK_USER_PASSWORD`, `TTK_ADMIN_INVITE_CODE` и `TTK_JWT_SECRET`.

### Как устроено

- **Пароли** — bcrypt (cost 12), в базе только хеши. Политика: 8+ символов, буква и цифра, не больше 72 байт.
- **Access-token** — JWT на 30 минут, проверяется на каждом защищённом запросе.
- **Refresh-token** — JWT на 7 дней с ротацией: при обновлении старый токен отзывается. Повторное использование старого refresh-токена считается признаком кражи и отзывает все сессии пользователя. Небольшое 10-секундное окно не наказывает за параллельное обновление из двух вкладок.
- **Роли** — `user` и `admin`. Админские ручки (`GET /api/venues`, `PUT /api/venues/{slug}`, `POST /api/upload`) недоступны без роли администратора.
- **Выход** — инкрементирует версию токенов пользователя, поэтому мгновенно отзывает все access- и refresh-токены.
- **Хранилище** — SQLite в `backend/data/auth.db` (создаётся автоматически, переживает рестарт контейнера).

### Эндпоинты

| Метод | Путь | Назначение |
| :--- | :--- | :--- |
| `POST` | `/api/auth/register` | Регистрация `user` или `admin` (для админа — `adminInviteCode`) |
| `POST` | `/api/auth/login` | Вход по email/паролю; `role` проверяет, что открыт нужный портал |
| `POST` | `/api/auth/refresh` | Обновление пары токенов с ротацией refresh-токена |
| `POST` | `/api/auth/logout` | Выход и отзыв всех сессий |
| `GET` | `/api/auth/me` | Текущий пользователь |
| `POST` | `/api/auth/change-password` | Смена пароля с перевыпуском токенов |

Пример:

```bash
curl -X POST http://localhost:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@ttk.local","password":"Admin12345!","role":"admin"}'
```

Ответ содержит `accessToken`, `refreshToken` и `user`. Защищённые запросы — с заголовком `Authorization: Bearer <accessToken>`.

### Защита от перебора и базовая безопасность

- **5 неверных паролей** на аккаунт → блокировка на 15 минут.
- **30 неудачных попыток входа** с одного IP за 15 минут → временная блокировка IP.
- **10 регистраций** с одного IP в час.
- **120 запросов** ко всем `/api/auth/*` с одного IP в минуту — защита от флуда.
- JWT проверяется по подписи, `iss`, `aud`, сроку действия, типу токена и версии сессии.
- Единый ответ «Неверный email или пароль» и проверка хеша-пустышки не дают определить, зарегистрирован ли email.
- `X-Forwarded-For` учитывается только при `TTK_TRUST_PROXY=true`, иначе лимиты по IP нельзя обойти подделкой заголовка.
- CORS ограничен списком origin из `TTK_CORS_ORIGINS`, а не `*`.
- Добавлены `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, HSTS за HTTPS.
- Для `/uploads/*` включён CSP `sandbox`, чтобы загруженный SVG не мог исполнить скрипт на домене API.
- Ограничен размер JSON-запроса (1 МБ), загрузка файлов дополнительно ограничена 25 МБ.
- SQL-запросы параметризованы, имена загружаемых файлов и папок санитизируются, path traversal заблокирован.

Все параметры можно переопределить переменными окружения — они перечислены в `docker-compose.yml` и `backend/app/auth/config.py`.

## Статус проекта и что делать дальше

Этот раздел — для команды. Здесь честно написано, что уже работает, где стоят заглушки и какие шаги дадут сквозной демо-сценарий. Сначала закройте пункты с пометкой «критично», остальное — по времени.

### Сквозной сценарий, к которому идём

1. Организатор в админке (`:3001`) правит POI и граф, нажимает «Опубликовать».
2. Изменения реально сохраняются в бэкенд (`PUT /api/venues/{slug}`), а не остаются в React-state.
3. Бэкенд отдаёт площадку по slug и считает корректный маршрут.
4. Посетитель открывает ссылку/QR `/m/{slug}`, видит план, POI, маршрут и 360-панорамы.
5. Панорамы, сшитые `cv-worker`, подхватываются бэкендом и клиентом автоматически.

Сейчас цепочка разорвана в трёх местах: админка не сохраняет, клиент не читает API, `cv-worker` не связан с бэкендом. Ниже — что делать по папкам.

### Контракт панорам от cv-worker

`cv-worker` складывает результаты в `/app/uploads/panoramas` и уже отдаёт всё нужное наружу. Бэкенду и клиенту не нужно сканировать файлы — читайте `index.json`.

`index.json`:

```json
{
  "generatedAt": "2026-10-24T08:00:00+00:00",
  "count": 1,
  "panoramas": [
    {
      "id": "lobby",
      "type": "panorama",
      "url": "/uploads/panoramas/lobby.webp",
      "previewUrl": "/uploads/panoramas/lobby_preview.webp",
      "width": 1802,
      "height": 901,
      "previewWidth": 1024,
      "previewHeight": 512,
      "floorId": "floor-1",
      "x": 600,
      "y": 400,
      "yawOffset": 0,
      "hotspots": []
    }
  ]
}
```

Что это значит для команды:

- **Бэкенд**: добавьте `GET /api/panoramas`, который читает `index.json` и отдаёт его как есть; либо при публикации площадки переносите записи из `index.json` в `Venue.floors[].panoramas` по `floorId`.
- **Клиент**: берите `previewUrl` для быстрого старта, `url` — для полного качества, `hotspots` — для хотспотов Pannellum.
- **Админка**: после загрузки кадров обновляйте список панорам из `index.json`, а `x/y/floorId` задавайте при публикации.
- **Все**: поля манифеста совпадают с `Panorama` из `shared/types.ts`, так что маппинг минимальный.

### Общие правила, чтобы не сломать демо

- Работаем каждый в своей папке; общие контракты (`shared/types.ts`, `mock_venue.json`) меняем только по согласованию.
- Любое изменение API сначала фиксируем в `shared/types.ts`, потом в коде.
- Не хардкодим `localhost` в клиенте и админке — только env.
- Перед коммитом проверяем, что `docker compose up --build -d` поднимает все 4 сервиса.
- Не коммитим секреты и локальные пути (`file:///c:/...`) в код.

4. Положили 2–3 кадра в `data/uploads/<name>/` — в `data/uploads/panoramas/` появились `<name>.webp` и `index.json`.
