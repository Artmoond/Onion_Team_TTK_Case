# Интеграция редактора с общими типами, backend и клиентом

Документ фиксирует, как `frontend-admin` работает с существующим контрактом
`shared/types.ts` и API backend. Общие файлы не изменялись: все расширения
добавлены только в локальные типы редактора и являются опциональными.

## 1. Совместимость с `shared/types.ts`

Базовые сущности `Venue`, `Floor`, `POI`, `Panorama`, `NavGraph`, `Hotspot`
сохраняют исходные поля и смысл. Редактор читает `shared/mock_venue.json`
без миграции и умеет вернуть его обратно в совместимом виде.

| Сущность | Поле | Статус | Назначение |
| --- | --- | --- | --- |
| `POI` | `panoramaId` | опционально | Связь точки с 360° панорамой |
| `POI` | `wifi` | опционально | SSID, пароль, тип защиты |
| `POI` | `info` | опционально | Ссылка и расписание |
| `POI` | `entrance` | опционально | Направление и доступность |
| `POI` | `wardrobe` | опционально | Часы работы и вместимость |
| `POI` | `other` | опционально | Произвольные поля для своего типа |
| `Floor` | `planAsset` | опционально | Метаданные загруженного плана |
| `Floor` | `walls` | опционально | Стены с длиной в метрах |
| `Floor` | `rooms` | опционально | Полигоны помещений |
| `Floor` | `stairs` | опционально | Лестничные марши и связи этажей |
| `Venue` | `schemaVersion` | опционально | Версия расширенной схемы, сейчас `1` |
| `Venue` | `publicUrl` | опционально | Публичная ссылка, если её вернул backend |
| `Panorama` | `asset` | опционально | Метаданные загруженной панорамы |
| `Stair` | `x1`, `y1`, `x2`, `y2` | локальное расширение | Ось лестничного марша в пикселях |
| `Stair` | `width` | локальное расширение | Ширина марша в пикселях |
| `Stair` | `direction` | локальное расширение | `up`, `down` или `both` |
| `Stair` | `targetFloorId` | опционально | Этаж, с которым связана лестница |
| `Stair` | `targetStairId` | опционально | Парная лестница на другом этаже |

Категории точек расширены значениями:

```ts
'panorama' | 'info' | 'wardrobe' | 'other'
```

Правила совместимости:

- frontend-client должен уметь игнорировать незнакомые опциональные поля;
- незнакомую категорию следует показывать как `service`/`other` с исходной
  подписью, если она доступна;
- если клиент не поддерживает `walls`/`rooms`/`stairs`, он может рисовать только
  `planUrl`, `points`, `panoramas`, `graph`;
- координаты остаются в пикселях плана, как в `shared/mock_venue.json`;
- `metersPerPixel` — обязательный источник истины для перевода пикселей в метры;
- `graph` редактор сохраняет и валидирует: рёбра без существующих узлов
  отбрасываются, остальные не пересчитываются.

```json
            "fileName": "panorama.webp",
            "mimeType": "image/webp",
            "sizeBytes": 102400,

```

`AssetReference.storage` принимает `local` или `server`.

- `local` + `local-asset://<id>` — файл лежит в IndexedDB браузера редактора.
- `server` + `/uploads/...` или абсолютный URL — файл доступен всем.

Бинарные данные в JSON не попадают. Пользователь не выбирает и не сохраняет
JSON-файлы вручную: редактор формирует эти данные автоматически при публикации.

## 3. API, который использует редактор

Новые endpoint не добавлялись. Используются только существующие маршруты backend.

### `GET /api/health`

Проверка доступности backend в верхней панели.

### `GET /api/venues`

Список площадок для открытия в модалке «Открыть карту с сервера». Редактор
нормализует каждую запись через `normalizeVenue`.

### `GET /api/public/{slug}`

Реальная публичная карта. Редактор напрямую её не вызывает, но публикует данные
в формате, который этот endpoint возвращает клиенту.

### `POST /api/upload`

`multipart/form-data`, поле `file`.

Ответ:

```json
{ "url": "/uploads/asset-...-panorama.webp", "size": 102400 }
```

Редактор делает URL абсолютным относительно `VITE_API_URL`, затем подставляет
его в `planUrl`/`panorama.url`/`panorama.previewUrl`.

### `PUT /api/venues/{slug}`

Тело — полный JSON площадки. Ответ backend:

```json
{ "status": "saved", "slug": "demo-ttk" }
```

Редактор не полагается на формат ответа, кроме успешного HTTP-статуса.

## 4. Поток публикации

1. Пользователь нажимает «Опубликовать на backend».
2. Редактор собирает уникальные локальные `AssetReference`.
3. Каждый файл читается из IndexedDB и загружается через `POST /api/upload`.
4. В копии данных `storage` меняется на `server`, URL — на ответ backend.
5. Обновляются `floor.planUrl`, `panorama.url`, `panorama.previewUrl`.
6. Выполняется `PUT /api/venues/{slug}`.
7. Backend сохраняет карту и только после этого возвращает `publicUrl`; редактор
   добавляет его к опубликованной версии и показывает ссылку и QR-код.
8. Локальное состояние заменяется опубликованной версией, чтобы повторная
   публикация не содержала `local-asset://`.

Если локальный файл отсутствует в IndexedDB, публикация останавливается с
понятной ошибкой. Это намеренно: подставить несуществующий файл нельзя.

## 5. Публичная ссылка и QR

Публичный URL создаёт backend в успешном ответе `PUT /api/venues/{slug}`.
Админка не показывает ссылку и не активирует скачивание QR до успешного ответа.
База ссылки задаётся переменной backend `PUBLIC_MAP_BASE_URL` (по умолчанию
`http://localhost:3000`); backend добавляет к ней `/m/<slug>`.

## 6. Что нужно от frontend-client

- Читать `GET /api/public/{slug}` и использовать `planUrl`/`planAsset.url`.
- Поддерживать базовые POI и `panoramas`; неизвестные категории не должны
  ломать рендер.
- Если поддерживается 360°, использовать `panorama.url`, `previewUrl`,
  `hotspots`, `yawOffset`.
- Опционально рисовать `walls`, `rooms` и `stairs`; при отсутствии полей
  использовать только план и точки.
- Для лестниц использовать `x1`, `y1`, `x2`, `y2`, `width`, `direction`, а
  `targetFloorId`/`targetStairId` — как подсказку для перехода между этажами.
- Учитывать `metersPerPixel` для расстояний.
- Ссылку `/m/<slug>` должен обслуживать роутер клиента.

## 7. Что нужно от backend

- Сохранять и возвращать опциональные поля без потери данных.
- `PUT /api/venues/{slug}` должен сохранять площадку под slug из URL; редактор
  всегда отправляет совпадающие slug в URL и теле, но backend полезно проверить
  это явно.
- `POST /api/upload` должен возвращать стабильный URL, доступный по `/uploads`.
- Желательно санитизировать имена файлов и ограничивать размер; редактор уже
  отправляет безопасное имя и ограничивает размер на клиенте
  (план — 12 МБ, панорама — 25 МБ).
- Для production нужны авторизация, постоянное хранилище и `publicUrl` в ответе.
- Текущий MVP-маршрут использует только первый этаж; для многоэтажных карт
  алгоритм нужно расширить.

## 8. Миграция и устойчивость

- `normalizeVenue` заполняет отсутствующие `walls`, `rooms`, `stairs`,
  `planAsset`, `schemaVersion`, `graph` и настройки точек.
- Некорректные или несуществующие связи `targetFloorId`/`targetStairId`
  очищаются, парные лестницы восстанавливаются в двустороннюю связь.
- Неизвестная категория сохраняется как `other` с исходной подписью.
- Дубликаты `floor.id` перегенерируются, дочерние объекты получают новый
  `floorId`.
- `lengthMeters` стен и площади помещений пересчитываются из координат и
  `metersPerPixel`; хранимые значения не считаются истиной.
- Загрузка с backend проверяет наличие хотя бы одного этажа и корректность данных.
- Черновик хранится в `localStorage` под ключом `ttk-admin:draft:v1`;
  локальные файлы — в IndexedDB `ttk-admin-assets`.

## 9. Проверка интеграции

```bash
cd frontend-admin
npm run typecheck
npm run test
npm run build
```

Тесты сериализации читают настоящий `shared/mock_venue.json` и проверяют, что
контракт не меняется, а расширенные поля проходят round-trip.

Для ручной проверки:

1. Открыть демо-карту.
2. Добавить второй этаж, нарисовать стены цепочкой и лестницы.
3. Связать лестницы между этажами и проверить переход.
4. При запущенном backend опубликовать площадку и открыть
   `GET /api/public/<slug>`, проверив наличие `walls`, `rooms`, `stairs`.
